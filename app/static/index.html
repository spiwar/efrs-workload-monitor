This monitor shows an EFRS operations / performance lead how long events tie up crews and apparatus and where and when that workload concentrates — always against a multi-year norm, so drift is visible. It informs; the lead decides.

The one rule that matters

Every duration in this app is event handling time — dispatch→close: the time an event file was open, from first dispatch to the last unit clearing. The dataset has no arrival and no call-received timestamp, so this app never shows a response time, time-to-arrival, or NFPA benchmark — asking for one is declined and logged, by design.

How to use each page

  • ② Overview — the current window at a glance: KPI cards, handling-time distribution, volume by hour / weekday, a weekday×hour heatmap, top neighbourhoods, units dispatched, a "biggest shifts" table, and a choropleth map of areas running above their own norm. Hover any chart for exact values; click a map area for its numbers; use the map's Hotspots/All toggle.
  • ③ Forecast — a transparent seasonal projection of volume only for the next 6 months with an ~80% interval, plus projected event-hours. It is an extrapolation with uncertainty, never a causal claim. Date/hour filters do not apply here (it uses full monthly history).
  • ④ Ask the data — plain-language questions ("when is medical busiest downtown?", "how should I plan crews for downtown fire?"). Decision-support answers describe demand patterns; unsupported asks (response times, station performance) are refused and logged.

Filters (top bar, apply everywhere except Forecast)

  • Period + From/To date — pick a year and an exact date range inside it. The 5-year baseline automatically uses the same date range in the 5 prior years, so every comparison stays like-for-like. The latest year is capped at the data cutoff.
  • From/To hour — restrict to a time-of-day band (e.g. 15:00–18:59); the baseline follows the same band.
  • Event type / UNKNOWN — filter to one event type; include or exclude events whose neighbourhood is recorded as the literal value UNKNOWN (~13% of rows).
  • ⟳ Refresh data — pulls the newest rows from Edmonton Open Data (the city updates the dataset daily, so "live" here means daily-fresh, not real-time). The clock shows the newest event in the data.

Data source

City of Edmonton Open Data — Fire Response (Current and Historical), dataset 7hsn-idqi, 2011→present, one row per dispatch event. Non-incident administrative records (training/maintenance, community events, pre-incident planning, permit burning) are excluded from every metric. Timestamps are parsed with fixed rules; negative/zero durations are dropped.

Limitations — read before acting

  • No response times. Handling time (dispatch→close) cannot say how fast crews arrived.
  • The latest year is partial. It is only ever compared year-to-date vs the same window in prior years.
  • Locations are approximate. Events are geocoded to the nearest intersection; the app never goes below neighbourhood level.
  • Counts are dispatches, not workload-hours. Units dispatched are unit types, not identified apparatus or crews; there is no station field.
  • Monitoring, not inference. No causal or predictive claims; the forecast is a labelled volume extrapolation.
